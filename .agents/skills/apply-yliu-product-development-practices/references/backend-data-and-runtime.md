# 数据、后端与运行

设计数据库、实现后端接口或准备生产环境时，使用本规范。

## 选择数据库和访问方式

- 数据库优先在 PostgreSQL 和 SQLite 之间选择。
- 本地工具、单机应用和低并发场景优先考虑 SQLite。多用户、服务端和并发场景优先考虑 PostgreSQL。
- 优先使用适配当前技术栈的成熟 ORM，减少手写和维护 SQL 的成本。
- 查询复杂、需要性能优化，或者 ORM 无法清楚表达时，可以使用参数化原生 SQL。

## 验证数据和处理时间

- 前后端输入优先使用 Zod 等成熟的 Schema 方案校验。尽量复用类型和验证规则，不要前后端各写一套。
- 数据库存储时间统一使用 UTC，不依赖开发机、CI、容器和服务器的本地时区。
- 展示数据时，再转换为用户所在时区。产品只面向国内用户时，默认使用 `Asia/Shanghai` 展示。
- 编写时间相关测试和定时任务时，明确考虑 CI 与生产环境的时区差异。

## 统一后端响应

- 普通 JSON 接口统一返回 `data`、`message` 和 `code`。
- 使用全局中间件或拦截器包装成功结果，并统一捕获错误。业务处理函数只需要返回业务数据或抛出错误。
- 已知业务错误转换为稳定的业务错误码和可读消息。未知错误只向用户返回安全的通用消息。
- 保留正确的 HTTP 状态码，不要把失败伪装成成功。文件下载和流式响应可以不使用普通 JSON 包装。

## 提供接口文档

- HTTP 后端默认提供 OpenAPI 文档和 Swagger UI。
- 优先根据路由和 Zod 等 Schema 自动生成文档，避免分别维护接口实现、验证规则和文档。

## 管理环境变量

- 环境变量尽量提供合理默认值，让项目在默认配置下可以运行。
- 配置没有安全合理的默认值，而且必须由部署方提供时，才设为必填。应用启动时应当校验这些配置。
- 提供简洁的 `.env.example`。只列出需要了解或覆盖的配置，不写入真实凭证。

## 输出日志

- 根据消息的重要程度，使用 Debug、Info、Warn 和 Error 等日志级别。
- 开发环境输出适合人阅读的日志，并用不同颜色区分级别。
- 生产环境向 `stdout` 和 `stderr` 输出结构化 JSON 日志。日志不带 ANSI 颜色，方便 Docker 和日志平台采集。
- 生产日志使用 UTC ISO 8601 时间。日志包含级别、服务、消息和可用的请求上下文，错误日志保留排查问题所需的信息。
- 不要在容器内部长期保存日志文件。Docker Compose 需要配置日志轮转，避免日志占满磁盘。

## 编排生产环境

- 用户没有指定，而且项目也没有既定部署方案时，生产环境默认使用 Docker Compose 编排。
- 使用正式构建的镜像和生产配置，不挂载开发源码。
- 在 Compose 中声明需要的服务、环境变量、端口、网络和持久化数据。
- 旧项目已经有稳定部署方式时，继续沿用。不要主动迁移到 Docker Compose。
