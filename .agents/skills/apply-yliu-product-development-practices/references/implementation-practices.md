# 实现与抽象

编写 TypeScript、组织目录、拆分文件或提取公共代码时，使用本规范。维护注释和 README 时也使用本规范。

## 控制修改范围

- 默认沿用项目已有风格，不顺便重构、改写相邻注释或调整无关格式。每处改动都应能说明它与当前任务的关系；用户明确授权的重构按授权范围执行。
- 删除因本次修改而不再使用的 import、变量和函数，避免留下无用代码。
- 发现原本就存在的无关死代码或可改进之处时，可以指出，但不要顺手清理。

## 保持类型可信

- 不要用 `any` 绕过 TypeScript 类型检查。
- 输入类型确实未知时，先使用 `unknown`。完成类型收窄、校验或解析后，再读取其中的数据。
- 优先复用前后端共享类型，或者从可靠来源推导类型。不要在多个位置维护容易失去同步的重复声明。

## 复用业务和界面

- 可复用的业务逻辑、请求流程和状态变化，优先拆成 Hook 或 Composable。
- 一个 Hook 或 Composable 只解决一个清晰的问题。输入和输出只保留真正需要的内容。
- 如果一个 Hook 只是转发参数，没有让调用方更简单，就不要增加这层包装。无关业务也不要放进同一个抽象中。
- 界面重复出现，而且结构和交互已经稳定时，再提取公共组件。
- 不要为了覆盖所有场景，做出依赖大量属性的万能组件。
- 看到重复代码时先别急着抽象。只有抽象后更容易理解和维护，才值得复用。

## 组织目录和文件

- 顶层按照较大的公共模块组织，例如 `utils`、`hooks`、`components`、`services` 和 `pages`。
- 真正跨业务复用的代码放在较高层。只服务于某个业务或页面的代码，放到对应目录的更深层。
- `pages` 可以继续按照路由和业务嵌套。代码的适用范围越小，位置越靠近使用它的地方。
- 人工维护的源码尽量控制在 400 行以内。文件接近或超过 400 行时，先检查是否混入了多个职责。
- 400 行是提醒拆分的检查线，不是硬性限制。生成文件、Migration 和大型静态数据不需要机械拆分。

## 编写必要注释

- 注释使用用户和项目主要采用的语言。
- 如果业务意图、约束、算法或技术取舍无法从代码中直接看懂，应当补充注释。
- 代码已经表达清楚的内容不要再解释。没有实际信息的模块说明也不需要编写。
- 注释保持少而必要，不追求数量或覆盖率。

## 维护 README

- README 应当简洁、克制，并参考成熟开源项目的组织方式。
- 优先说明项目用途、安装和启动方法、必要环境变量、常用命令，以及确实需要的构建或部署信息。
- 源码和配置已经表达清楚的内容不要重复说明。不要维护多份含义相同的文档。
