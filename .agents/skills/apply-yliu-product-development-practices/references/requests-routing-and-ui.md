# 请求、路由与界面

组织接口、拆分路由、处理页面请求或编写界面时，使用本规范。

## 选择请求方案

- 项目已经有稳定的请求方案时，继续沿用。
- 新的前后端分离项目可以使用 Axios。
- Hono 同构项目优先使用 Hono RPC Client（`hc`），直接复用服务端类型。
- 页面优先使用 `useRequest` 或项目已有的请求 Hook。让成熟方案管理数据、Loading、Error、刷新、取消和生命周期，不要重复手写一套状态。

## 组织接口和错误

- 每个接口使用独立的 `export const` 异步函数。不要把大量接口聚合进一个庞大的 API 对象。
- 接口函数只返回页面需要的业务数据。Axios 通常返回 `res.data`；如果统一响应又包装了一层 `data`，则返回 `res.data.data`。
- 先从类型、请求封装和实际响应中确认业务成功规则，不要自行猜测成功码。
- 请求失败必须进入错误流程。不要把失败包装成正常返回的 `{ error }`。
- 统一请求层负责整理错误，页面负责展示反馈。同一个错误只提示一次。
- 错误消息要让用户看得懂，同时不能暴露堆栈、SQL、内部路径和敏感信息。

## 拆分页面和管理请求

- 按照业务职责拆分路由页面，不要把互不相关的功能堆在同一个页面中。
- 路由页面优先使用懒加载，避免提前初始化不需要的页面代码和请求。
- 每个页面只管理自己的请求和依赖。公共 Hook 不能顺便启动其他页面的接口。
- 请求依赖发生变化时，重新获取对应数据。参数快速变化时取消旧请求，或者忽略旧结果，避免旧数据覆盖新页面。
- 详情页和上下级资源使用 `/projects/:projectId/items/:itemId` 这类 URL 表达核心状态。页面根据 URL 参数请求数据。
- 不要依赖上一页临时保存在本地状态中的完整对象。详情页在刷新、直接访问和分享链接时，都应当独立加载。
- URL 只保存定位页面所需的状态，不放入完整业务对象和敏感信息。

## 展示反馈和异步状态

- 列表和详情等自动查询成功时，不显示“查询成功”。
- 用户点击确认后发起的新建、编辑和删除操作，成功时可以显示对应消息。
- 请求失败不能隐藏。页面使用 `message.error` 或当前 UI 框架的同类能力展示错误。
- 页面要区分首次加载、后台刷新、失败、空数据和正常内容。失败不能显示成“暂无数据”，必要时提供重试入口。
- 哪个区域正在请求，就由哪个区域显示 Loading。已有内容刷新时保留内容，只显示轻量加载状态。
- 使用 Skeleton、占位结构或稳定容器，减少加载前后的布局塌陷和抖动。
- 新建、编辑和删除正在执行时，禁用对应操作，避免重复提交。

## 处理危险操作

- 删除、退出登录等危险操作需要二次确认。
- 单条且影响清楚的操作，优先使用气泡确认。批量、不可逆或需要解释影响的操作，使用对话框。
- 确认按钮写明具体动作。请求期间显示 Loading，并禁止重复点击。

## 编写样式

- 没有设计稿时，优先使用适配当前框架的成熟 UI 组件库，例如 Ant Design 或 Element Plus。组件库负责主要界面和交互。
- 新项目使用 UnoCSS 或 Tailwind CSS 辅助组件库，处理布局、间距和局部定制。
- 旧项目继续使用现有样式体系。本次修改涉及的局部可以逐步适配，但不要主动迁移无关样式。
- 只有用户明确要求整体重构时，才系统替换旧样式。
- 优先使用原子类、组件属性、主题变量和设计 Token。
- 复杂状态、动画或难以表达的样式，可以使用局部 `style` 或 CSS。
- 不要依赖脆弱的选择器，强行覆盖 UI 组件库的内部实现。
